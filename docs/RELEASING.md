# Releasing NullBot UI

## Changelog convention

Write and commit `docs/changelog/vX.Y.Z.md` for every release. Describe user-visible changes, fixes, dependencies, platform requirements, and known limitations. That file is the release description source of truth; the local script appends build provenance automatically.

Update `frontend/package.json`, the root package entries in `frontend/package-lock.json`, and `wails.json` `info.productVersion` together. Pin public Go dependency commits/tags in `go.mod` and commit `go.sum`; do not ship local replace directives or workspace overrides.

## Local automation

The optional PowerShell script `scripts/release-local.ps1` is deliberately gitignored and machine-local (not included in clones). Build prerequisites: Go, Node/npm with frontend dependencies installed from the lockfile, Wails CLI, and GitHub CLI for publication.

```powershell
# From nullbot_ui, after reviewing and committing release changes:
.\scripts\release-local.ps1 -Version v0.4.0
# For a future version, build and publish in one pass only after security review:
.\scripts\release-local.ps1 -Version vX.Y.Z -Publish
```

The script checks version metadata, a clean main branch, absence of frontend `.env*` / `VITE_*` overrides, and its own ignore rule; verifies Go modules; runs Go/frontend tests; builds Windows amd64 with trimmed paths; and packages an explicit executable-only ZIP and SHA256 checksums under ignored `build/releases/<version>/`. Existing version output is never overwritten. The generated release notes append module/build provenance. `-Publish` explicitly pushes only main and the new tag and creates the GitHub release from those notes. It does not push stashes or backup branches.

If Wails regenerates tracked bindings, review and commit those changes, then rerun. If publication fails after a tag was pushed, inspect GitHub and resume manually; never force-move an existing released tag.

## Security and verification gate

- Review staged filenames and diffs. Never use broad staging to include runtime data.
- Scan tracked source, new docs, regenerated frontend assets, and the executable for credential patterns; investigate findings without printing secret values. Pattern scans are heuristic, not a guarantee.
- Confirm Vite regenerates `frontend/dist` with only expected assets; Go embeds that whole directory.
- Never package whole build/workspace folders. Only upload the executable, executable-only ZIP, and checksums.
- Keep `.nullbot`, profiles, authentication JSON, `.env` files, private keys, local release scripts, and test output out of Git and release assets.
- Local stashes may contain credentials; they are not release inputs and must not be pushed/exported.
- Verify release asset hashes and inspect Windows version metadata. Record whether interactive GUI/live-provider smoke tests were performed.

Manual publication uses `gh release create <tag> <explicit assets> --verify-tag --notes-file build/releases/<tag>/RELEASE-NOTES.md`; do not use autogenerated notes in place of the curated changelog.
